Introducao
Visao geral do pvSolar Auth

O pvSolar Auth e o modulo de autenticacao e autorizacao do ecossistema pvSolar. Oferece autenticacao baseada em JWT com refresh tokens, controle de acesso baseado em funcoes (RBAC), gerenciamento de chaves API e isolamento multi-tenant.

JWT Tokens
Access e refresh tokens com revogacao e blacklist.
RBAC
5 funcoes padrao e 9 permissoes granulares.
Multi-Tenant
Isolamento por tenant com limites e features.
API Keys
Geracao, validacao e revocacao de chaves.
Rate Limiting
Limite por IP e por tenant.
Seguranca
Lockout, historico de senhas, politica de complexidade.

Fluxo de Autenticacao

  • 1. Usuario envia credenciais via POST /api/auth/login
  • 2. UserManager valida credenciais e retorna TokenPair
  • 3. Client envia access token em cada requisicao
  • 4. Access token expira apos 30 minutos (configuravel)
  • 5. Client usa refresh token para obter novo access token
  • 6. Refresh token expira apos 7 dias (configuravel)
Funcionalidades
Modulos do sistema

User Manager

CRUD completo para gerenciar usuarios:

  • Criar, listar, atualizar, excluir usuarios
  • Autenticacao com senha (PBKDF2-SHA256 + salt)
  • Lockout apos 5 tentativas falhas
  • Gerenciamento de API keys

Auth Engine

Gerenciamento de tokens JWT:

  • Access tokens (30 min padrao)
  • Refresh tokens (7 dias padrao)
  • Revogacao de tokens (blacklist)
  • Sessoes multi-dispositivo

RBAC Engine

Controle de acesso baseado em funcoes:

  • 5 funcoes padrao: super_admin, admin, operator, viewer, api
  • 9 permissoes granulares
  • Politicas customizaveis
  • Hierarquia de funcoes

Tenant Manager

Gerenciamento multi-tenant:

  • CRUD de tenants
  • Limites de usuarios por tenant
  • Features habilitadas por tenant
  • Isolamento de dados

Banco de Dados
PostgreSQL (opcional)

A persistencia e opcional: com database.enabled: false o servico roda somente em memoria (comportamento original). Quando ativa, usuarios, tenants, chaves de API, funcoes RBAC e o estado de lockout sao gravados em PostgreSQL e sobrevivem a reinicios do servico.

1. Configurar a URL
# Opcao A: config/auth.yaml database: enabled: true url: "postgresql+asyncpg://postgres:senha@localhost:5432/pvsolar_auth" # Opcao B: variavel de ambiente (tem prioridade sobre o YAML) set PVSOLAR_DATABASE_URL=postgresql+asyncpg://postgres:senha@localhost:5432/pvsolar_auth
2. Criar o banco (uma vez)
python scripts\create_databases.py
3. Iniciar o servico
uvicorn src.app:app --host 0.0.0.0 --port 8007 # O schema e criado automaticamente no startup (create_tables: true)

Comportamento no startup

  • Cria as tabelas caso nao existam (idempotente)
  • Carrega usuarios, tenants, chaves de API e funcoes do banco para a memoria (hydrate)
  • As funcoes do banco substituem as 5 funcoes padrao quando ha registro
  • Cria o usuario seed (admin) somente se o banco estiver vazio - nunca duplica

Gravacao (write-through)

  • POST/PUT/DELETE de usuarios, tenants e funcoes grava na mesma requisicao
  • POST /api/auth/login persiste tentativas e lockout (protecao contra brute force sobrevive a reinicio)
  • Se a gravacao falhar, a API retorna 500 e a mudanca em memoria e desfeita (sem divergencia)

usersUsuarios, hash de senha, papel, tentativas e lockout
api_keysChaves de API vinculadas ao usuario

VariavelDescricao

Scripts utilitarios

python scripts\create_databases.py # cria o banco (uma vez) python scripts\reset_database.py --yes # dropa todas as tabelas (dev)

Para validar a persistencia em testes: python -m pytest tests/ -v (usa SQLite por padrao). Para rodar contra o PostgreSQL real, aponte para o banco de testes dedicado - os testes dropam o schema a cada execucao:

set PVSOLAR_TEST_DB_URL=postgresql+asyncpg://postgres:senha@localhost:5432/pvsolar_auth_test python -m pytest tests/ -v
Autenticacao
Login e tokens JWT

Login

POST /api/auth/login Content-Type: application/json { "username": "admin", "password": "admin123" } Response: { "access_token": "eyJ...", "refresh_token": "eyJ...", "token_type": "bearer", "expires_in": 1800 }

Renovar Token

POST /api/auth/refresh Content-Type: application/json { "refresh_token": "eyJ..." }

Logout

POST /api/auth/logout Authorization: Bearer eyJ...
Nota
O refresh token e invalidado no logout. O access token continua valido ate expirar.

Multi-Tenant
Isolamento por organizacao

Cada tenant e isolado com seus proprios usuarios, configuracoes e limites.

Criar Tenant

POST /api/tenants { "name": "Empresa ABC", "slug": "empresa-abc", "plan": "enterprise", "max_users": 50, "features": ["dashboard", "alerts", "reports"] }

Gerenciar Features

PUT /api/tenants/{tenant_id}/features { "feature": "analytics", "enabled": true }
Atencao
Cada tenant tem seu proprio banco de dados. Nao ha compartilhamento de dados entre tenants.
API Keys
Autenticacao via chaves

Criar Chave

POST /api/api-keys { "name": "Pipeline CI/CD", "user_id": "user-uuid", "scopes": ["read", "write"], "expires_days": 90 } Response: { "id": "key-uuid", "key": "pvs_ak_xxxxxxxxxxxx", "name": "Pipeline CI/CD", "scopes": ["read", "write"] }
Importante
A chave so e exibida uma vez na criacao. Salve-a em local seguro!

Validar Chave

# Headers da requisicao Authorization: Bearer pvs_ak_xxxxxxxxxxxx

Seguranca
Melhores praticas
Senhas
PBKDF2-SHA256 com salt aleatorio.
Lockout
Conta bloqueada apos 5 tentativas falhas (15 min).
Historico
Ultimas 5 senhas nao podem ser reutilizadas.
Expiracao
Senhas expiram apos 90 dias.
HTTPS
Obrigatoria em producao.
Rate Limit
100 req/min por IP.
Producao
Use HTTPS, altere a chave JWT, configure CORS adequadamente e use banco criptografado.
